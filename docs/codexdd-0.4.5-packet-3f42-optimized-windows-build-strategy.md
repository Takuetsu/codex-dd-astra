## Grounded constraints and failure mode

1. Historical optimized [Windows run #40693489522](https://github.com/Takuetsu/codex-dd-astra/actions/runs/40693489522) analyzed `//codex-rs/cli:release_files` successfully but was canceled at the workflow's 90-minute job limit, just before completing 2,858 Bazel actions (per captured build log). The old workflow used `--config=ci-windows-msvc`, which imports `common:ci --disk_cache=` from `.bazelrc`, **without a separate persistent disk-cache setup**. A fresh hosted runner therefore starts a cold release build every time. Raising the timeout *alone* is not a checkpointing strategy.
2. Real optimized [3F.28 run #40739170655](https://github.com/Takuetsu/codex-dd-astra/actions/runs/40739170655) successfully built `//codex-rs/utils/elapsed:elapsed` with MSVC `--config=release` and thin LTO. Runner 1: 5 local compilation actions; runner 2: **5 Bazel disk cache hits, 0 local**; exact stable PATH hash `7e3457c3218c6933b8b30de65061ccf56c951619862e7d4f38ed9f2be086908e`; cache 8,492,218 bytes. The original job remained red solely because its receipt verifier used stdout-only logs; the historical [3F.31 audit #40741387319](https://github.com/Takuetsu/codex-dd-astra/actions/runs/40741387319) independently verified the native results and passed.
3. `codex-rs/cli:release_files` explicitly requires one `codex.pdb` through Bazel's Windows `pdb_file` output group. `//codex-rs:runtime_package_combined` contains five executables and their PDBs under current upstream packaging definitions: `codex`, `codex-app-server`, `codex-code-mode-host`, `codex-command-runner` and `codex-windows-sandbox-setup`. The Windows sandbox service and responses proxy are separately packaged upstream and are not implied to be in the combined archive. Do not change official package membership while fixing caching.

## Three measured gates before expensive release compilation

**Gate A — source/toolchain security and archive policy (cheap Linux):**
- Lock source HEAD, `MODULE.bazel`, Bzlmod lock, `Cargo.toml`, `Cargo.lock`, `deny.toml`, runtime packaging transition and 109-owner audit; staging marker 0.4.4, upstream marker 0.162.0, no release promotion.
- Test `scripts/codexdd_045_verify_windows_archive.py` against synthetic valid/invalid fixtures: exact five EXE + five PDB, no paths/duplicates/symlinks, no extra executables, real PE and MSVC PDB magic, nonempty content, SHA-256 receipts. These **synthetic unit tests are not optimized binary proof**.

**Gate B — independent larger-than-elapsed real optimized Rust cache probe (bounded Windows):**
- Two different hosted `windows-2022` runners compile the **actual** `//codex-rs/config:config` Rust library with release opt/thin-LTO/4-CGU. Bind to exact source SHA and locked tools and normalize only the irrelevant hosted Ruby path *after* loading the preinstalled MSVC developer environment. Both runners must produce identical action `PATH` SHA-256. Fail if the toolchain/SDK source identity differs.
- Unlike immutable helper cache keys, use an **explicit immutable per-run stage key** for `actions/cache/save` and `actions/cache/restore`. Select `--disk_cache=D:/_bazel-disk` on Bazel command line to override the inherited `common:ci --disk_cache=`. Cap transmitted cache to 1 GiB, fail closed on exceeding the bound. Require at least one disk-cache hit and **zero local rebuild actions** on runner 2; require both compiles succeeded and matching release flags. Record cache size and action summary. If capacity limits, transport failures, or PATH drift occur, stop; do not advance to an optimized CLI build.

**Gate C — staged full optimized build (NOT YET AUTHORIZED):**
- On **one frozen source SHA**, create chained Windows jobs/steps with successive fresh cache keys: `warm` → `cli` → `combined`. A stage must restore the previous stage's exact cache and save a fresh key after successful completion. The runner must not rely on an immutable cache key already populated by a previous job. A job can be given sufficient headroom (within GitHub-hosted runner limits) but must emit its own bounded progress, disk-space and cache-size receipts. Do not split a Rust binary *link action* across runners: an incomplete link is not a cacheable checkpoint; allow it enough time **within one job** once the heavy Rust dependencies are warm.
- Stage `cli` builds `//codex-rs/cli:release_files`; require actual **nonempty `codex.exe` and `codex.pdb`**. Stage `combined` then builds `//codex-rs:runtime_package_combined` using cached CLI outputs; inspect the actual `runtime_package_combined.tar.gz` with `scripts/codexdd_045_verify_windows_archive.py`, write a SHA-256 inventory of all ten payloads and the archive itself, and upload only nonrelease diagnostics/checksums (binary publishing remains prohibited until acceptance).
- A previous job's cache transport success is not evidence that it reused compiler actions. Every stage must establish actual Bazel cache hits, version/platform identity, source SHA, bounds and real artifact checks. Use secret-free caches; no production credentials, installer signing keys, config files or test-user artifacts in disk cache.

**Gate D — final acceptance later:** semantic owner signoff for all 109 overlapping paths, source-frozen native Windows startup/daemon/WSL and authorization regression matrix, complete 21-stage local Daniel-CL suite, verified archive distribution including separate components if required, then PR merge/signing/install. Do not label staging 0.4.5 READY until these succeed.

This packet prepares the reusable archive validator and measured Gate B. It **does not execute Gate C**, rerun the 90-minute cold CLI build, publish binaries, or alter CodexDD 0.4.4 installed on Daniel-CL, Stonks or Doug.
