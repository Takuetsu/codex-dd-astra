# CodexDD 0.4.3 — packet 3A.2: additive conflict-recovery contract

**Status:** CONTRACT DESIGN CHECKPOINT — source/workflow bridge **not implemented**, no promotion authority conferred. Gate 2 approved isolated reconciliation on 2026-10-09. This document specifies the only acceptable **future** additive lane for the actual `rust-v0.162.0` textual conflicts.

## 1. Why 0.4.2 clean-only contracts are insufficient

Current production `.github/scripts/upstream_sync.py` emits candidate manifest **v1** and treats `transplant_dry_run=conflict` as `state=blocked_transplant_conflict`. `.github/workflows/upstream-prepare.yml` exits before publishing a candidate when conflicts exist. `.github/workflows/upstream-promote.yml` accepts only v1 `preparation_ready` or `manual_semantic_review_required`; `scripts/codexdd-validate-upstream-candidate.ps1` also explicitly requires manifest `contract_version=1` and an exact deterministic canonical branch.

The [new completed read-only discovery](https://github.com/Takuetsu/codex-dd-astra/actions/runs/37960772252) definitively has **22 conflicts**, so it cannot satisfy the v1 clean-only contract. Relabeling the failed discovery as clean, replacing it with hand-edited v1 `manual_semantic_review_required`, or invoking the original publish/promotion workflow is **forbidden**.

The bridge must be a **versioned, additive** reconciliation lane. Unchanged, valid v1 clean candidates must still be accepted without a reconciliation sidecar; v1 conflicted candidates must still be rejected.

## 2. Names and states

- **Discovery v1 evidence (immutable):** retain the blocked original manifest and exact 22-path conflict report as individually SHA-256-bound GitHub Actions artifacts. Do **not** change these bytes or states.
- **Reconciled candidate manifest v2 (new):** `contract_version: 2`, `state: manual_conflict_reconciled_review_required`, `transplant_dry_run: conflict`, explicit discovery evidence digest fields and the sidecar path/digest. It must carry the current-base and upstream Git commit/tree identities, the full 136-path overlap inventory and per-category sensitivity risk. The new state is never generated by `candidate_state("conflict", ...)`.
- **Reconciliation sidecar v1 (new):** `attestation_type: codexdd_upstream_conflict_reconciliation`, `contract_version: 1`; committed under `docs/upstream-candidates/` beside the v2 candidate manifest. It binds every conflict and resolution to the exact **blocked** discovery, accepted production base, tracked/target commits/trees, source snapshot commit/tree, ownership map, overlap audit, and test/semantic-review evidence.
- **Receipt v2 (new, only for reconciled path):** `contract_version: 2`, `receipt_type: codexdd_upstream_local_validation`, mandatory `profile: release` and native PASS, candidate branch/HEAD, production baseline, target identity, manifest path/hash, reconciliation sidecar path/hash and source snapshot commit/tree. The existing v1 receipt parser remains available for v1 clean candidates.
- **Canonical candidate branch:** `automation/upstream-candidate-rust-v0.162.0-c1382380de69`, once only. **Never** use the isolated source-development branch directly as a promoted candidate.

All new JSON artifacts require canonical serialized UTF-8, strict types, no duplicate JSON keys, no non-finite numeric fields, SHA/hex validation, path confinement, and explicit rejection of unknown contract state/type combinations. Exact schema and complete rejection tests must be implemented **before** the bridge is used for a candidate.

## 4. Source snapshot and metadata finalization

To avoid a circular attestation-that-hashes-its-own-commit:

1. Resolve all source changes on `dd/codexdd-v0.4.3-upstream-0.162.0-integration`. Separately validate source, generated artifacts, product and upstream provenance. Record final **source snapshot commit** and its Git tree.
2. Freeze the snapshot. Record the snapshot commit/tree in the typed sidecar and bind all 22 conflict decisions and the complete overlap audit to this snapshot. Source semantics cannot change afterward without restarting this binding.
3. Prepare a **metadata-only** commit on the candidate path containing exactly the immutable v2 manifest, sidecar and separately approved evidence. Verify the source snapshot is an ancestor and `git diff` from snapshot to candidate contains only the allowlisted evidence paths; its refs must still descend from the current production SHA.
4. A dedicated **publish-once**, absence-guarded bridge checks candidate ref absence both before and during publication, re-verifies original discovery, production and target official refs, source snapshot and attestation, then creates the exact canonical candidate branch from production ancestry without replacing an existing ref.
5. After canonical candidate publication and owner acceptance Gate 2B, run Daniel-CL `scripts/codexdd-validate-upstream-candidate.ps1 -Profile release` with additive v2 support. The produced v2 receipt must bind canonical candidate HEAD, manifest and sidecar SHA-256 and the native profile result.
6. Promotion on production must understand v2 and verify all bytes/identities again. It may open only a **review PR**, with explicit owner semantic acceptance and a same-repository GitHub review link. CI and owner approval remain required for merge/install.

**No implicit conversion:** `blocked_transplant_conflict` always remains nonpromotable. Only a new fully validated v2 sidecar/manifest pair can be considered for a different, explicitly reviewed reconciled-path state.
