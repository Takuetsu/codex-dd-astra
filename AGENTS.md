## Current 0.4.6 delivery-throughput rules — 2026-11-10 (workflow only)

This adapts BREAKWATER's owner-approved 2026-11-10 throughput recovery and the existing staged Workflow V3 to CodexDD development. It does **not** activate BREAKWATER work, replace CodexDD with standard Codex, waive a security/validation gate, authorize a production merge/install, or thaw 0.4.5. Full rationale: [0.4.6 throughput-recovery adaptation](docs/codexdd-0.4.6-throughput-recovery-adaptation-2026-11-10.md).

- **One useful outcome:** each authorized packet targets one observable CodexDD reliability behavior or one evidence-backed defect class. Start with a short card: exact branch/base/SHA, owning layer, user-visible outcome, acceptance criterion, cheapest meaningful proof, exclusions, STOP conditions, and next permitted action. Link to current source/doc authorities instead of copying historical chat.
- **Classify before fixing:** A = confirmed in-scope product/security/persistence defect; T = test/oracle/harness defect; E = environment/tool/profile/permission; U = missing or conflicting causal evidence; B = unrelated backlog. Record OBSERVED, EXPECTED, smallest REPRO, identity, evidence and owning path. Do not edit production code on U or turn an E/T failure into product-repair authority.
- **No-progress circuit breaker:** never rerun unchanged CI, cargo suites, diagnostics or tool setup just to obtain another receipt. After **two attempts on the same objective with no new discriminating evidence or authorized progress**, stop that approach; preserve logs and return the missing fact and one genuinely different next diagnostic/owner decision. A changed source, hypothesis, environment or measured evidence may justify a new attempt. Safety-critical holds remain in force.
- **Staged validation:** cheap focused checks and necessary negative controls during implementation/repair, Daniel-CL/local-first under the rules below, and source-matched reuse of valid existing evidence. When a safe disposable runtime candidate exists, an **explicitly owner-authorized** early agent smoke may provide preliminary usability proof; it is not independent acceptance. Fresh nonauthor scoped review precedes packet/gate acceptance. Full official Windows release/E2E/security/21-stage gates remain at final integrated candidate acceptance before promotion, never waived.
- **Progress is completed utility:** report a working approved behavior, a newly discriminated blocker or genuine repair—not packet count, models, commits, tokens or 50-minute CI loops. Keep concise handoffs and preserve earlier red/INCOMPLETE results without relabeling them green.
- **Authority boundary:** current BREAKWATER Z-A0.58 is separately paused and normal-Codex-only by its own owner governance; this is context, not an instruction to switch or resume that game. CodexDD remains on its dedicated 0.4.6 development branch, with 0.4.4 production and frozen 0.4.5 untouched.

- The assistant makes all GitHub-side source/design/documentation changes and commits. The operator only supplies limited Windows validation through SSH to Daniel-CL; do not ask the operator to edit source or use RDP.
- After each source work packet, perform the **smallest cheap relevant local test on Daniel-CL first**, before broad GitHub CI. Use the native Local Validation Orchestrator's `targeted` or `work_packet` receipt where supported. When validating an uninstalled integration candidate, supply short, non-destructive PowerShell commands for the operator to execute over SSH.
- If local tests fail, repair GitHub-side code, then repeat only affected cheap Daniel-CL checks. **Do not use GitHub Actions as a routine remote debugging loop or create throwaway CI workflows for feasible local diagnostics.**
- Use GitHub Actions for the **final relevant CI gate after local validation passes**. A GitHub-only exception needs a documented reason local testing is unavailable and explicit owner approval. A failed final CI requires log triage, narrow repair, and cheap local retest before intentionally running CI again.
- The release candidate's **native Windows release profile and live F2/daemon/resume behavior** are separate owner-gated checks. CI success is not a substitute. Source semantic acceptance, candidate publication, production merge, install and release remain separately authorized.
- Use read-only GitHub reconnaissance freely when needed, avoid unnecessary Rust tests for docs-only changes, preserve exact source SHA evidence, and do not modify production as a side effect of unapproved integration.

This file is a durable project-specific instruction for future CodexDD agents. It does not itself grant release or production permissions.
